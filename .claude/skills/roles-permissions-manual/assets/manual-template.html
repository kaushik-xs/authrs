1 · The big picture

Access is granted in a simple chain — read it left to right:

Permissionwhat can be done
→
Rolea named bundle
→
User / Groupthe people who get it
  • A permission says what someone may do (e.g. "view materials").
  • A role is a named bundle of permissions (e.g. "Dispatch Manager").
  • A user receives a role — directly, or by belonging to a group that has the role.
Golden rule: never give a permission straight to a person. Put permissions into a role, then give the role to people. It stays tidy, reusable, and auditable.

2 · The words we use

TermPlain meaning
TenantThe customer's isolated workspace. Nothing is shared between tenants.
UserA person's membership inside one tenant. Roles are given to this membership.
GroupA set of users (a team/department). A role given to a group reaches every member.
RoleA named bundle of permissions. Can inherit from a parent role.
PackageA product area that ships entities, e.g. Manufacturing Essential, Siemens, Jobq.
EntityA type of record inside a package, e.g. Materials, Tickets, Projects. Access is granted on entities.
PermissionA rule that allows (or blocks) a set of actions on one or more entities.
ActionOne thing that can be done, e.g. view materials, create a ticket. The "permission name".
Access levelA convenient grouping of actions: Viewer, Editor, Admin.

3 · How access is decided

When a person tries to do something, the system checks their roles and returns Allow or Deny. Two rules matter:

  1. Default is "No". If nothing explicitly allows the action, it is blocked.
  2. A block always wins. If one rule allows and another blocks, the block takes priority. Use a block for firm exceptions (e.g. "everything on tickets except delete").

4 · The three access levels

Almost everything is granted at one of three levels. Pick the lowest level that lets someone do their job.

LevelCan doCannot doGive it to…
ViewerView / list recordsAny changePeople who only need to see data
EditorView, Create, Edit, ArchiveDelete, RestoreDay-to-day operators
AdminEverything incl. Delete & Restore—Owners of that data area
Note: Editor can archive (hide) records but cannot permanently delete or restore them. Only Admin can delete and restore — this protects data from accidental loss.

6 · Permission names — how access is named

Behind each access level is a set of precise action names. You rarely type them, but support teams should recognise them.

Naming rule: action name = verb + EntityName (EntityName with no underscores, each word capitalised).
e.g. entity materials → getMaterials; entity bom_materials → getBomMaterials.
VerbExample (Materials)MeaningIn which level
getgetMaterialsView / listViewer, Editor, Admin
postpostMaterialsCreateEditor, Admin
patchpatchMaterialsEdit part of a recordEditor, Admin
putputMaterialsReplace / full updateEditor, Admin
archivearchiveMaterialsArchive (soft-delete)Editor, Admin
deletedeleteMaterialsPermanently deleteAdmin only
unarchiveunarchiveMaterialsRestore an archived recordAdmin only

Custom actions — some packages add special actions beyond the seven above. In this environment there is one: reopenMilestoneTicket (Manufacturing Essential) — lets a user reopen a closed milestone ticket. Custom actions are granted with their own dedicated permission.

7 · Ready-made permission building blocks

Every package ships pre-built permissions so you don't assemble actions by hand. Two shapes:

ShapeName patternWhat it covers
Whole-package<Package> - <Level>That level across all entities. e.g. Siemens - Viewer, Jobq - Admin
Per-entity<Package> - <Entity> <Level>That level for one entity. e.g. Manufacturing Essential - Materials Editor

Levels are always Viewer Editor Admin. When building a role, add the blocks it needs — mix whole-package and per-entity freely.

9 · Who a permission applies to

SettingMeaningWhen to use
Everyone with this role recommendedWorks for whoever holds the role it's attached toAlmost always. Control access by which role you attach it to.
A specific roleOnly members of a named roleRare.
A specific userOnly one named personExceptions and one-offs.
The ready-made building blocks already use Everyone with this role, so access is controlled purely by which role you add them to.

10 · Optional conditions

Conditions add an extra requirement that must be true for a permission to apply.

ConditionEffect
Requires MFA verifiedThe action only works if the user completed multi-factor sign-in.
Restricted to a tenantThe action only applies within a specific workspace.

Use conditions to gate sensitive actions such as delete or reopen.

11 · Setting up access — step by step

This walkthrough follows the real console screens. Open IAM from the left sidebar — it has three areas: Users, Roles and User Group. There is no separate "Permissions" area — permissions are attached inside a role.

The panels below are faithful representations of the actual console screens (real role and building-block names).

1

Open IAM

Click IAM in the left sidebar. The fly-out shows Users, Roles and User Group.

2

Review existing roles

Open IAM → Roles. Each row shows the Access Role, what it Inherits From (its parent), and its attached Permissions as chips. Use List or Tree view.

3

Create the role

Click + Create. Enter a unique Role name and, optionally, a Parent role — "the new role inherits all permissions from its parent (and the parent's ancestors)." Click Create role. (Permissions are added next.)

4

Attach permission building blocks

Open the role to bring up its Permissions dialog. Under Attached Permissions, the current building blocks appear as chips (click × to detach). Add more from the picker, then Save.

5

Pick the blocks from the list

Type to search, or scroll the picker. Blocks are named <Package> - <Level> (whole package) or <Package> - <Entity> <Level> (one entity) — e.g. Jobq - Admin, Jobq - Job Editor. Selecting one attaches it directly to the role.

6

Give the role to people — option A: a user

Open IAM → Users, open the user, and add the role under their roles. Use this for individuals. (Create users here, or Bulk Upload.)

7

Give the role to people — option B: a group

Open IAM → User Group, click the edit (pencil) on a group, and add roles under Roles for this group. "All current and future members inherit roles assigned to this group" — the best way to manage teams.

After any change, have the affected people sign out and back in so their session picks up the new access.

13 · Best practices

  • Grant through roles, not individuals. Keep "Applies to" as Everyone with this role.
  • Prefer the ready-made building blocks over hand-built permissions.
  • Least privilege. Start from Viewer; move to Editor/Admin only where needed.
  • Use whole-package blocks sparingly — mostly for admins. Everyday roles should list specific entities.
  • Use groups for teams. Onboarding becomes "add the person to the group".
  • Reserve Admin (delete/restore) for data owners. Editors can already archive.
  • Use a parent role to avoid repeating a big permission list.
  • Always run the permission check after wiring up a role.

15 · Troubleshooting

SymptomLikely causeFix
User can't do something they shouldThe block wasn't added, or the role isn't assignedCheck the role has the right entity + level, and the user/group holds the role.
User can view but not editThey only have a Viewer blockAdd the Editor block for that entity.
User can edit but not delete/restoreEditor can't delete; that's AdminAdd the Admin block for that entity.
Still can't after grantingA Block permission is overriding itLook for a Block rule on that action; blocks always win.
Access changed but user unaffectedTheir session predates the changeHave them sign out and back in.
Right role, still deniedA condition isn't met (e.g. MFA)Check the permission's conditions (§10).
